Регламент процесса разработки и ввода в эксплуатацию программной системы

Проект: Система управления продажами пищевых продуктов (Food Sales Management System) Команда: Учебная группа № ИСП-301 Платформа: Azure DevOps Server / Git Статус: Согласовано

Введение. Назначение документа

Настоящий документ устанавливает единые правила, стандарты и процедуры организации жизненного цикла разработки, контроля версий, обеспечения качества, формирования релизов и ввода в эксплуатацию программной системы «Система управления продажами пищевых продуктов».

Регламент обязателен для исполнения всеми участниками проектной группы и базируется на методологиях Microsoft Solutions Framework (MSF), Extreme Programming (XP) и стандартах управления версиями Team Foundation Version Control / Azure DevOps Repos.

Специфика предметной области: Продажа пищевых продуктов

Программная система автоматизирует процессы розничных и мелкооптовых продаж продуктов питания. Особенности продовольственной торговли определяют критические инженерные требования:

  • Партионный учет и контроль сроков годности (принцип FEFO — First Expired, First Out): система обязана отслеживать даты производства и сроки годности каждой партии товара, блокируя продажу просроченной продукции на кассовом узле.
  • Непрерывность кассовых операций (High Availability): простой кассового узла магазина недопустим. Операции пробития чеков и расчета должны происходить со временем отклика < 0.5 сек.
  • Запрет отрицательных остатков: блокировка отпуска товара при отсутствии фактического остатка на выбранном складе.
  • Интеграция с торговым оборудованием: сканеры штрихкодов, весы с печатью этикеток, фискальные регистраторы.

1. Выбор и обоснование ЖЦ разработки процесса. Ролевой состав

1.1. Выбор методологии процесса разработки

Для организации инженерного процесса внутри команды выбран легковесный гибкий фреймворк Extreme Programming (XP, Экстремальное программирование).

💡 Обоснование выбора XP для студенческой группы

В соответствии с указанием руководителя («если люди не ходят, лучше XP»), главным риском студенческого коллектива является неравномерная посещаемость и риск внезапного выбывания участников. В тяжеловесных процессах (RUP, Waterfall) узкая специализация приводит к остановке проекта.

XP устраняет «Bus Factor» за счет следующих практик:

  1. Коллективное владение кодом (Collective Code Ownership): в проекте нет «чужого кода». Любой участник команды имеет право и обязанность модифицировать любой модуль системы продаж (кассу, склад, расчет скидок).
  2. Парное программирование (Pair Programming): работа в парах гарантирует, что контекст задачи знают как минимум двое. Если один студент пропускает занятия, второй продолжает работу без потери темпа.
  3. Разработка через тестирование (TDD) и CI: наличие исчерпывающих автоматических тестов гарантирует, что участник, вернувшийся после пропуска, не сломает бизнес-логику коллег.
  4. Простой дизайн (Simple Design): исключает оверинжиниринг на ранних этапах.

1.2. Ролевой состав команды (3–5 человек) и совмещение ролей

В малой проектной команде роли участников совмещаются:

1.3. Регламент динамического изменения ролей

  • Матрица взаимозаменяемости: в случае невыхода на связь участника более 24 часов его задачи со статусом Active переводятся Менеджером на дублирующего разработчика.
  • Автоматический пропуск Code Review: согласно стандарту (Лекция 10), если на активности Development и Code Review назначен один и тот же исполнитель, шаг ревью пропускается автоматически.
  • Ротация пар: состав пар разработчиков меняется каждые 3–4 дня для выравнивания знаний по всем подсистемам.

2. Выбор и обоснование ЖЦ проекта

2.1. Разграничение понятий

ЖЦ процесса разработки (Раздел 1) регламентирует внутреннюю ежедневную деятельность инженеров (XP, TDD, коммиты).
ЖЦ проекта определяет макроструктуру фаз проекта во времени от замысла до передачи заказчику и критерии прохождения контрольных точек (Milestones).

2.2. Обоснование фазово-итерационной модели MSF Process Model

Для системы управления продажами выбрана модель Microsoft Solutions Framework (MSF), состоящая из 5 фаз с контрольными вехами:

Фаза MSF Ключевые активности в проекте продаж продуктов Контрольная веха (Milestone)
1. Выработка концепции (Envisioning) Формирование бизнес-требований к розничным продажам, определение границ проекта (Scope), оценка первоначальных рисков порчи данных. Концепция проекта утверждена (Vision & Scope Approved)
2. Планирование (Planning) Проектирование структуры БД (товары, склады, чеки), описание PBI в Azure DevOps, разработка архитектурного плана и стратегии миграции. План проекта утвержден (Project Plan Approved)
3. Разработка (Developing) Итеративная реализация спринтами (по 2 недели): ядро номенклатуры $\rightarrow$ кассовый узел $\rightarrow$ партионный учет FEFO $\rightarrow$ отчеты. Код заморожен (Scope Complete / Code Freeze)
4. Стабилизация (Stabilizing) Сквозное тестирование в ветке Release Candidate, проверка отказоустойчивости кассы, устранение дефектов, верификация скриптов миграции БД. Релиз готов к выпуску (Zero Bug Bounce)
5. Развертывание (Deploying) Установка в магазине, первичное наполнение справочников, обучение кассиров, пилотная эксплуатация, передача в Service Desk. Ввод в эксплуатацию завершен (Deployment Complete)

3. Выбор и обоснование процесса, методики или практик управления

3.1. Практики оперативного управления (Scrum-спринты)

  • Длина спринта: 2 календарные недели.
  • Оценка трудозатрат: оценка в часах методом Planning Poker. Обязательное заполнение полей рабочего элемента: Original Estimate (план), Remaining Work (остаток, ежедневно), Effort (факт).
  • Ежедневный стендап (15 минут): фиксация прогресса и оперативное выявление препятствий (Impediment).
  • Ретроспектива спринта (Лекция 10): закрытие спринта созданием рабочего элемента Retrospective со снимками Task retrospective для корректного расчета списания часов при переносе незавершенных задач.

4. Описание Артефактов проекта, их иерархии и определение точки окончания задачи (DoD)

4.1. Иерархия рабочих элементов (Work Items) в Azure DevOps

Epic: Управление продажами и складским учетом продуктов питания │ ├── Feature: Партионный учет и контроль сроков годности (Feature Type = Module) │ ├── Estimation Point (Total Effort = 64h, Dev Effort = 40h) │ │ │ ├── PBI-101: Регистрация поступления партии скоропортящегося товара с фиксацией даты годности │ │ ├── Task 1: Requirements (Анализ полей сертификатов и дат) │ │ ├── Task 2: Development (Создание сущности Batch, миграция БД) │ │ ├── Task 3: Code Review (Архитектурный контроль) │ │ ├── Task 4: Inner Deployment (Выкладка на Dev-стенд) │ │ └── Task 5: Testing (Проверка граничных дат в UI) │ │ │ └── PBI-102: Блокировка добавления в чек товара с истекшим сроком │ └── Tasks (Requirements -> Development -> Code Review -> Deploy -> Testing) │ └── Feature: Кассовый интерфейс и оформление фискального чека (Feature Type = Architectural)

4.2. Жизненный цикл задачи и механизм команды #FIX (Лекция 10)

По каждому PBI задачи выполняются строго в заданной последовательности. В случае обнаружения дефектов процесс регламентирован следующими правилами:

  • Замечания на этапе Code Review: ревьюер пишет в поле History команду #FIX, название правки и описание. Создается связанный рабочий элемент REVISION PBI с задачей Development. Родительская задача Code Review блокируется: Blocked = Yes.
  • Дефекты на этапе Testing: тестировщик пишет в History команду #FIX со шагами воспроизведения. Создается рабочий элемент REVISION BUG, блокирующий задачу тестирования (Blocked = Yes). После исправления дефекта создается задача Inner Deployment для обновления стенда.

4.3. Определение точки окончания задачи (Definition of Done — DoD)

Уровень Критерии завершения (Definition of Done)
Task (Development) Код написан, Unit-тесты пройдены, Changeset привязан к Task, Remaining Work = 0, статус Closed.
Task (Code Review) Замечания отсутствуют либо все REVISION устранены, блокировка снята, статус Closed.
Product Backlog Item (PBI) Все 5 подзадач закрыты, функционал проверен на Dev-сервере по тест-плану, критических багов нет, PBI переведен в Done (или Committed).
Sprint / Release Код слит в Release Candidate, применены миграции БД, автотесты зеленые, сгенерированы Release Notes, получено подтверждение от Product Owner.

5. Управление структурой версий проекта, иерархией веток и слиянием

5.1. Рекомендованная структура веток Source Control (Лекция 11)

[Main] ────────────────────────────────────────────────────────────────────────► (Базовый ствол) │ ├─► [Development] ──────────────────────────────────────────────────────────► (Интеграция разработки) │ │ │ ├─► [Feature_BatchInventory] ─── (Разработка учета партий) │ └─► [Feature_CashierPOS] ─────── (Разработка кассы) │ └─► [Release Candidate] ────────────────────────────────────────────────────► (Тестовый стенд магазина) │ └─► [Release] ───────────────────────────────────────────────────────► (Промышленная среда касс)
⚠️ Главное правило промышленной ветки

Ветка Release всегда строго соответствует версии, работающей в промышленной эксплуатации на кассах магазинов! Прямые коммиты в Main и Release запрещены политиками ветвления (Branch Policies).

5.2. Правила слияния (Merge Policies)

  1. Ввод новой фичи: Feature $\rightarrow$ Main $\rightarrow$ Release Candidate (RC). На тестовом сервере проводится приемочное тестирование. После подтверждения готовности код из RC переносится в Release.
  2. Вывод новой функциональности на тест: перед выкладкой новой ветки Feature в нее обязательно подтягиваются свежие изменения из RC.
  3. Исправление багов в поддержке (Support Hotfix): баг правится в ветке RC, тестируется, и после подтверждения заказчиком протаскивается в Release и во все активные ветки Feature.
  4. Комментарий к коммиту слияния: строго по шаблону Merge from <Source> to <Target> с привязкой задачи на слияние и сохранением номеров в поле Changesets.

5.3. Схема формирования номеров версий

Формат версии ПО (согласно Лекции 11): <ИмяВетки>_<Major>.<Minor>.<Revision>.<BuildNumber>

Пример боевого релиза: Release_1.4.2.1450

  • Major (1): мажорная версия. Увеличивается при смене архитектуры (Feature Type = Architectural), минорные сбрасываются.
  • Minor (4): количество завершенных PBI. Инкрементируется на +1 автоматически при переводе задачи разработки PBI в статус Done.
  • Revision (2): счетчик исправлений дефектов (REVISION / багфиксов).
  • BuildNumber (1450): номер автоматической сборки CI или номер Changeset.

6. Управление версионностью структурой данных хранилищ (БД)

6.1. Организация веток базы данных в Source Control

Схемы БД хранятся параллельно с исходным кодом в репозитории:

  • Prod Copy DB — снимок рабочей схемы промышленной базы магазина.
  • RC DB — схема и тестовые данные для стенда приемочного тестирования.
  • Feature DB — изолированная схема для разработки фичи.

6.2. Регламент переноса изменений через SNAP-файлы (Лекция 11)

🛑 Правило слияния базы данных

«Слияние БД выполняется через SNAP-файл (DACPAC / Schema Snapshot) с обязательной проверкой на БД той версии, к которой приливаются изменения.»

Запрещается применять миграции напрямую к промышленной базе без предварительной тестовой накатки на актуальной копии Prod Copy DB.

6.3. Синхронизация версий миграций с номерами релизов

Каждый SQL-скрипт именуется строго в соответствии с номером версии ПО:

db/migrations/
├── V1_0_0__Initial_Products_And_Categories.sql
├── V1_1_0__Create_Batches_And_Expiration_Dates.sql
├── V1_2_0__Add_POS_Check_And_Check_Items.sql
└── V1_2_1__Fix_Rounding_Tax_Issue.sql

Политика безопасных изменений схемы:

  • Запрещены деструктивные операции (DROP COLUMN, DROP TABLE) в рамках минорных версий.
  • Применение паттерна Expand & Contract: сначала добавляется новая колонка (например, BarcodeEan13), старая помечается устаревшей, и лишь через мажорный релиз старое поле удаляется.
  • Исключение перетирания данных: перетирание БД на сервере категорически запрещено. Любое изменение выполняется инкрементальными обратимыми скриптами.

7. Описание процессов интеграции автоматизированного и ручного тестирования

7.1. Шесть этапов процесса тестирования (Лекция 11)

  1. 7.1. Поверхностное тестирование (Smoke Test): экспресс-проверка базовой работоспособности после каждого билда (запуск кассы, авторизация кассира, открытие смены).
  2. 7.2. Формирование тест-плана: создание тест-кейсов в Azure Test Plans по каждому PBI спринта.
  3. 7.3. Ручное визуальное тестирование: тестирование удобства кассового интерфейса, сканирования штрихкодов, проверка печати чеков.
  4. 7.4. Покрытие автоматическими тестами: сквозные UI/E2E-тесты (Playwright/Selenium) на сценарии: добавление товара в корзину, расчет скидки, отказ в продаже просрочки.
  5. 7.5. Модульное (Unit) тестирование серверной части: покрытие бизнес-логики расчета налогов, проверки сроков годности $Date_{exp} \ge Today$ и списания остатков (целевое покрытие ≥ 80%).
  6. 7.6. Доработка тест-плана: актуализация проверок после устранения выявленных багов.

7.2. Автоматизация в CI пайплайне (Лекция 11, стр. 12)

При каждой сборке и выкладке на внутренний тестовый сервер конвейер автоматически формирует и рассылает участникам проектной группы Отчет тест-плана:

  • Список новых задач, готовых к тестированию в данной сборке.
  • Список задач, исключенных из тестирования (не прошедших этап Code Review).
  • Список исправленных дефектов (Revision Bugs).
  • Перечень Changeset'ов со времени последней успешной сборки.

7.3. Причины закрытия неактуальных дефектов

Если баг не подтвердился при повторном тестировании ветки Release Candidate, он закрывается с указанием причины в поле Reason:

  • As Designed — функционал работает согласно измененным требованиям;
  • Cannot Reproduce — дефект не воспроизводится на актуальной сборке;
  • Duplicate — дефект уже зарегистрирован под другим номером.

8. Описание процессов и требований формирования выпусков версий, процедура развёртывания

8.1. Критерии готовности выпуска (Release Quality Gates)

  • Все PBI, запланированные в релиз, находятся в статусе Done;
  • Все задачи Code Review закрыты, отсутствуют открытые флаги блокировки Blocked = Yes;
  • 100% модульных и регрессионных тестов завершились успешно;
  • Отсутствуют открытые баги с критичностью Critical или Blocker;
  • Скрипты миграции схемы БД успешно прошли тестовое применение на копии промышленной БД.

8.2. Конвейер окружений развертывания

Среда Назначение Триггер развертывания
Inner Dev Test Внутренний сервер команды разработчиков для оперативной проверки задач. Автоматически при коммите в ветку Development.
Stage (RC Test) Тестовый стенд магазина, полностью воспроизводящий промышленное окружение. Автоматически при слиянии изменений в ветку Release Candidate.
Production Рабочие кассовые узлы и центральный сервер магазина. Вручную технологом/DevOps после сдачи вехи и согласования окна обновления.

8.3. Автоматическая генерация Release Notes (Stage)

При выкладке сборки на сервер Stage автоматически генерируется документ Release Notes, включающий список реализованных PBI, номера закрытых багов и перечень затронутых таблиц БД. Задачи в активности Stage Deployment закрываются автоматически.

8.4. Процедура развертывания и план отката (Rollback Plan)

  1. Фиксация контрольной точки: создание полного бэкапа базы данных Production и бинарных файлов перед обновлением.
  2. Перевод кассовых узлов в режим технического обслуживания (off-hours, с 23:00 до 06:00).
  3. Применение инкрементальных скриптов миграции БД.
  4. Развертывание бинарных пакетов новой версии сервисов.
  5. Прогон 5-минутного Smoke-теста (пробитие тестового чека, возврат).
  6. План отката: при сбое сборки или падении Smoke-теста в течение 10 минут выполняется восстановление БД из бэкапа и возврат на предыдущий стабильный релиз.

9. Описание процедуры ввода в эксплуатацию с учетом двух вариантов

📋 Общая нормативная процедура

Ввод в эксплуатацию регламентируется стандартом ГОСТ 34.601 и фазой Deploying модели MSF: подготовка инфраструктуры, обучение кассиров и товароведов, приемо-сдаточные испытания (ПСИ) и перевод на поддержку в Service Desk (с типами элементов Bug и Task согласно Лекции 12).

9.1. Вариант А: Замена существующей системы (Legacy Replacement — замена 1С / Excel)

Ключевая задача — не допустить остановки продаж магазина и сохранить непрерывность учета остатков:

  1. Аудит и сопоставление структур данных (Data Mapping): составление карты соответствия справочников старой системы (номенклатура, штрихкоды, поставщики) структуре новой БД. Очистка базы от дубликатов и неликвидных позиций.
  2. Разработка процедур миграции (ETL): написание скриптов автоматизированного переноса данных партий, остатков и цен; тестовый прогон миграции с замером времени выполнения.
  3. Стратегия перехода — Параллельная эксплуатация (Parallel Run):
    • В течение 7 календарных дней кассиры параллельно дублируют чеки в обеих системах (либо чеки бьются в новой, а в конце дня сверяется Z-отчет и баланс остатков).
    • Ежевечерняя сверка контрольных сумм по выручке, НДС и складским списаниям.
  4. Момент переключения (Cutover): проведение генеральной инвентаризации в ночь с воскресенья на понедельник, финальная дельта-выгрузка остатков, блокировка старой системы в режим Read-Only.
  5. Вывод старой системы из эксплуатации (Decommissioning): сохранение архивного слепка старой БД на изолированный носитель, отключение интеграционных шлюзов.

9.2. Вариант Б: Ввод в эксплуатацию новой системы (Greenfield Deployment — открытие нового супермаркета)

Исторические данные отсутствуют, упор делается на первичное наполнение справочников и подготовку персонала «с нуля»:

  1. Первичное наполнение нормативно-справочной информации (НСИ):
    • Импорт классификаторов товаров, категорий, единиц измерения;
    • Заведение номенклатуры с штрихкодами производителей;
    • Ввод начальных партий товаров от поставщиков с обязательным указанием сроков годности и цен реализации;
    • Заведение учетных записей кассиров, старших кассиров и товароведов с разграничением прав доступа.
  2. Обучение эксплуатационного персонала: проведение тренингов для кассиров (сканирование, безналичная оплата, аннулирование позиций, возврат продуктов) под руководством Технического писателя / QA.
  3. Опытно-промышленная эксплуатация (Пилотное внедрение): тестовая работа магазина в течение 3–5 дней в режиме «технического открытия» с ограниченным потоком покупателей; оперативное дежурство инженера на месте.
  4. Приемо-сдаточные испытания (ПСИ): выполнение контрольных сценариев по протоколу ПСИ в присутствии заказчика (преподавателя); подписание акта приемки.
  5. Перевод в режим промышленной эксплуатации: регистрация системы в службе Service Desk (Лекция 12); фиксация условий SLA: время реакции на критический сбой кассы не более 15 минут.
